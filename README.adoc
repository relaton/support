= Relaton support repository


== Purpose

This repository is used to store scripts and configuration for
the Git repositories belonging to https://github.com/relaton[Relaton].

== Contents

`*.[sh|ps1|bat]`:: different scripts used during build as part of CI workflow

`cimas-config/`:: configuration files for https://github.com/metanorma/cimas[Cimas]

`cimas-config/orphan-allowlist.yml`:: every Cimas-written file in a destination
  repo that `cimas.yml` no longer maps, and what was decided about it. Read by
  `bin/cimas-orphan-audit`. See "Cleaning up orphan files" below.

`bin/cimas-orphan-audit`:: reports what `cimas cleanup-orphan-files` would
  delete, before anyone runs it

`data-index/`:: source of truth for the `relaton-data-*` GitHub Pages index
  sites — each repo's branding and published index URL (relaton/relaton#48).
  See `data-index/README.adoc`.

`bin/gh-repo-manifest`:: (to be updated) script that generates/updates the
  `cimas-config/cimas.yml` file for the
  https://github.com/relaton[GitHub relaton organization]

=== Managing Cimas configuration (in `cimas-config/`)

The primary config file is `cimas-config/cimas.yml`.

Please see the Cimas configuration file format in
https://github.com/relaton/cimas[Cimas' README].


=== Running Cimas to synchronize CI configuration

You have to first install Cimas using:

[source,sh]
----
gem install cimas
----


These are the commands to run:

[source,sh]
----
cd relaton/support
export CIMAS_CONFIG=cimas-config/cimas.yml
export CIMAS_MASTER_DIR=cimas-config
export CIMAS_WD=~/src/relaton/cimas-wd

cimas setup -f $CIMAS_CONFIG -r $CIMAS_WD

cimas pull -f $CIMAS_CONFIG -r $CIMAS_WD \
  -g flavors,compiling

cimas sync -f $CIMAS_CONFIG -r $CIMAS_WD \
  -d $CIMAS_MASTER_DIR \
  -g flavors,compiling

cimas diff -f $CIMAS_CONFIG -r $CIMAS_WD -d $CIMAS_MASTER_DIR \
  -g flavors,compiling

cimas push -f $CIMAS_CONFIG -r $CIMAS_WD \
  -b cimas-initial-run -m 'Cimas initial run' \
  -g flavors,compiling

cimas open-prs -f $CIMAS_CONFIG -r $CIMAS_WD \
  -b cimas-initial-run -m 'Cimas initial run' \
  -g flavors,compiling
----


=== Cleaning up orphan files

`cimas sync` writes the files `cimas.yml` maps. It never deletes the ones it
stops mapping, so `cimas cleanup-orphan-files` does that instead. It deletes a
file on a two-part rule:

. the file's first 500 bytes carry `Auto-generated by Cimas`, so Cimas wrote it
  at some point, and
. the file's path is not a key of that repo's `files:` mapping, so Cimas no
  longer regenerates it.

Neither part is visible in this repo. **Dropping a mapping is therefore a delete
order** for every destination repo that still holds the file. The
`relaton-model-*` entries lost their model mapping in `31b3fda` with no note at
all, and two of those repos still ran the build those files drive
(relaton/support#65).

Two rules follow.

**Run the audit first.** `bin/cimas-orphan-audit` reports what a wave would
delete, over the GitHub API, and exits non-zero on an orphan that
`cimas-config/orphan-allowlist.yml` does not record:

[source,sh]
----
bin/cimas-orphan-audit                  # every repo; needs `gh`, logged in
bin/cimas-orphan-audit data             # one cimas group
bin/cimas-orphan-audit --all            # add the mapped and hand-owned rows
----

Judge every new row before the wave, and write the decision into
`orphan-allowlist.yml` — `keep`, `delete` or `review`. To see why a row says
`diverged`:

[source,sh]
----
bin/cimas-orphan-audit relaton-model-3gpp --only-target Makefile --show |
  diff -u cimas-config/gh-actions/model/Makefile -
----

**Never pass `--push-after` before the audit is clean.** Without that flag the
subcommand stages the deletions locally and pushes nothing, which is the second
gate: the audit reads the repo root and `.github/`, while Cimas walks the whole
working copy, so only the local run stages exactly what it would delete.

[source,sh]
----
cimas pull -f $CIMAS_CONFIG -r $CIMAS_WD -g models

cimas cleanup-orphan-files -f $CIMAS_CONFIG -r $CIMAS_WD -g models

git -C $CIMAS_WD/<repo> diff --cached     # review every deletion

cimas cleanup-orphan-files -f $CIMAS_CONFIG -r $CIMAS_WD -g models \
  --push-after -b cleanup-orphans-YYYY-MM-DD -m 'Remove orphan Cimas files'

cimas open-prs -f $CIMAS_CONFIG -r $CIMAS_WD -b cleanup-orphans-YYYY-MM-DD
----

Two traps in the scope:

* A repo that no group lists is reached by `-g all` and by no other `-g` value.
  The audit prints them.
* A repo whose `files:` is empty has *every* Cimas-written file orphaned, not
  one.


=== Un-mapping a file on purpose

Record it in `cimas.yml` where the mapping was:

[source,yaml]
----
    files:
      # unmapped 2026-09-03 (relaton/support#65): rake.yml is custom here. It
      #   runs the dependent-gem tests, which the shared template does not.
      # .github/workflows/rake.yml: gh-actions/master/rake.yml
      .github/workflows/release.yml: gh-actions/master/release.yml
----

`spec/cimas_unmapped_markers_spec.rb` fails on a comment inside a `files:` block
that starts no marker, and on a repo whose `files:` is empty and carries none.

The marker records the intent. It does not protect the file: only the
destination repo can do that, by deleting the two Cimas header lines, as
`relaton-data-itu` did for its `crawler.yml`. Until then the file needs a `keep`
row in `orphan-allowlist.yml`.
