= Relaton support repository


== Purpose

This repository is used to store scripts and configuration for
the Git repositories belonging to https://github.com/relaton[Relaton].

== Contents

`*.[sh|ps1|bat]`:: different scripts used during build as part of CI workflow

`cimas-config/`:: configuration files for https://github.com/metanorma/cimas[Cimas]

`cimas-config/orphan-allowlist.yml`:: every Cimas-written file in a destination
  repo that `cimas.yml` no longer maps, and what was decided about it. Read by
  `bin/cimas-orphan-audit`. See "Cleaning up orphan files" below.

`bin/cimas-orphan-audit`:: reports what `cimas cleanup-orphan-files` would
  delete, before anyone runs it

`data-index/`:: source of truth for the `relaton-data-*` GitHub Pages index
  sites — each repo's branding and published index URL (relaton/relaton#48).
  See `data-index/README.adoc`.

`bin/gh-repo-manifest`:: (to be updated) script that generates/updates the
  `cimas-config/cimas.yml` file for the
  https://github.com/relaton[GitHub relaton organization]

=== Managing Cimas configuration (in `cimas-config/`)

The primary config file is `cimas-config/cimas.yml`.

Please see the Cimas configuration file format in
https://github.com/relaton/cimas[Cimas' README].


=== Running Cimas to synchronize CI configuration

You have to first install Cimas using:

[source,sh]
----
gem install cimas
----


These are the commands to run:

[source,sh]
----
cd relaton/support
export CIMAS_CONFIG=cimas-config/cimas.yml
export CIMAS_MASTER_DIR=cimas-config
export CIMAS_WD=~/src/relaton/cimas-wd

cimas setup -f $CIMAS_CONFIG -r $CIMAS_WD

cimas pull -f $CIMAS_CONFIG -r $CIMAS_WD \
  -g flavors,compiling

cimas sync -f $CIMAS_CONFIG -r $CIMAS_WD \
  -d $CIMAS_MASTER_DIR \
  -g flavors,compiling

cimas diff -f $CIMAS_CONFIG -r $CIMAS_WD -d $CIMAS_MASTER_DIR \
  -g flavors,compiling

cimas push -f $CIMAS_CONFIG -r $CIMAS_WD \
  -b cimas-initial-run -m 'Cimas initial run' \
  -g flavors,compiling

cimas open-prs -f $CIMAS_CONFIG -r $CIMAS_WD \
  -b cimas-initial-run -m 'Cimas initial run' \
  -g flavors,compiling
----


=== Syncing one file, not a whole group

`cimas sync` writes *every* file a repo maps; `-g` selects repos, never files.
So repairing one workflow across the fleet drags every other mapped template
along with it. Measured on 2026-09-04, a plain `cimas sync -g data` would have
made functional changes to `deploy.yml` in 30 repos, `check-index.yml` in 30,
`crawler.yml` in 24 and `check_data.yml` in 3 — and wiped the per-repo `with:`
branding that `relaton-data-ecma`, `relaton-data-calconnect` and
`relaton-data-etsi` carry.

There is no `--only-target` on `sync` (`cleanup-orphan-files` has one; `sync`
does not). Narrow at the git level instead, between `sync` and `push`:

[source,sh]
----
cimas pull -f $CIMAS_CONFIG -r $CIMAS_WD -g data

cimas sync -f $CIMAS_CONFIG -r $CIMAS_WD -d $CIMAS_MASTER_DIR -g data

KEEP=.github/workflows/keep-alive.yml

# Keep one path; discard every other file cimas just wrote. Two steps, because
# `restore` only reaches files that were already tracked: sync creates an
# untracked file in any repo that did not have the mapped path yet.
for d in "$CIMAS_WD"/*/; do
  [ -d "$d/.git" ] || continue
  git -C "$d" restore --staged --worktree -- . ":!$KEEP"
  git -C "$d" ls-files --others --exclude-standard |
    grep -vxF "$KEEP" |
    while read -r f; do rm -f "$d/$f"; done
done

git -C $CIMAS_WD/relaton-data-rfcs status --porcelain   # spot-check one repo

cimas push -f $CIMAS_CONFIG -r $CIMAS_WD -g data \
  -b fix-keep-alive-target -m 'Point keep-alive at relaton/support'

cimas open-prs -f $CIMAS_CONFIG -r $CIMAS_WD -g data \
  -b fix-keep-alive-target -m 'Point keep-alive at relaton/support'
----

Three properties make this safe, none of them obvious from `cimas --help`:

* `sync` writes and stages into the working copies and **pushes nothing**.
  `push` is a separate command, so the narrowing step sits between them.
* `push` calls `reset_onto`, which is `git reset <base>` — a *mixed* reset, not
  `--hard`. Working-tree edits survive it, so the discarded files stay
  discarded and only the kept path is staged and committed. `-k` is not needed,
  and passing it would keep the wave branch from a previous run instead.
* `push` skips any repo whose `git status --porcelain` is empty, so repos that
  were already correct produce no branch and no PR.

The `.` before the `:!` exclusion is deliberate. A bare exclude-only pathspec
does work on git 2.50 — verified, not assumed — but older versions computed the
positive match first and returned "no match" when there was none, which would
make the `restore` a silent no-op and push the whole unscoped wave. The `.` is
a no-op where the bare form already works, so keep it.

Do not reach for `git clean` here. Its `-d` removes an untracked *directory*
whole, and an exclude pathspec does not protect a file inside one — a repo
receiving its first `.github/workflows/` file would lose the very file you meant
to keep. `ls-files --others` enumerates files, never directories, so the
exclusion holds. It leaves an empty directory behind, which git ignores.

`$CIMAS_WD` holds throwaway clones. Never run this loop over a checkout you
care about.

Verify with a `workflow_dispatch` run per repo rather than waiting for the next
cron. Check the result with `bin/cimas-orphan-audit --all --only-target <path>`.


==== When a repo has already been disabled for inactivity

GitHub disables a scheduled workflow after 60 days without repository activity.
A disabled workflow does not fire its cron and cannot be started by
`workflow_dispatch`, so **syncing a corrected file into such a repo does not
restore it**. `keep-alive.yml` is usually the workflow that would have prevented
this, which means it is usually disabled too and cannot re-enable itself.

Re-enable over the API first, then sync:

[source,sh]
----
gh api repos/relaton/<repo>/actions/workflows \
  --jq '.workflows[] | select(.state=="disabled_inactivity") | .id' |
  while read -r id; do
    gh api -X PUT "repos/relaton/<repo>/actions/workflows/$id/enable"
  done
----

To find them across the fleet before a wave. Take the slug from `CimasConfig`
rather than the `cimas.yml` key: `loc_marc` and `loc_mods` are keyed differently
from their GitHub names, and building the URL from the key 404s on both.

[source,sh]
----
ruby -Ilib -rcimas_config -e 'c = CimasConfig.load; puts c.names.map { |n| c.slug(n) }' |
  while read -r slug; do
    gh api "repos/$slug/actions/workflows" \
      --jq '.workflows[] | select(.state != "active") | "'"$slug"' \(.state) \(.path)"'
  done
----

An active repo never reaches this state: its own commits reset the clock. The
repos at risk are the dormant ones, where a broken keep-alive is invisible
precisely because nothing else runs there either.


=== Cleaning up orphan files

`cimas sync` writes the files `cimas.yml` maps. It never deletes the ones it
stops mapping, so `cimas cleanup-orphan-files` does that instead. It deletes a
file on a two-part rule:

. the file's first 500 bytes carry `Auto-generated by Cimas`, so Cimas wrote it
  at some point, and
. the file's path is not a key of that repo's `files:` mapping, so Cimas no
  longer regenerates it.

Neither part is visible in this repo. **Dropping a mapping is therefore a delete
order** for every destination repo that still holds the file. The
`relaton-model-*` entries lost their model mapping in `31b3fda` with no note at
all, and two of those repos still ran the build those files drive
(relaton/support#65).

Two rules follow.

**Run the audit first.** `bin/cimas-orphan-audit` reports what a wave would
delete, over the GitHub API, and exits non-zero on an orphan that
`cimas-config/orphan-allowlist.yml` does not record:

[source,sh]
----
bin/cimas-orphan-audit                  # every repo; needs `gh`, logged in
bin/cimas-orphan-audit data             # one cimas group
bin/cimas-orphan-audit --all            # add the mapped and hand-owned rows
----

Judge every new row before the wave, and write the decision into
`orphan-allowlist.yml` — `keep`, `delete` or `review`. To see why a row says
`diverged`:

[source,sh]
----
bin/cimas-orphan-audit relaton-model-3gpp --only-target Makefile --show |
  diff -u cimas-config/gh-actions/model/Makefile -
----

**Never pass `--push-after` before the audit is clean.** Without that flag the
subcommand stages the deletions locally and pushes nothing, which is the second
gate: the audit reads the repo root and `.github/`, while Cimas walks the whole
working copy, so only the local run stages exactly what it would delete.

[source,sh]
----
cimas pull -f $CIMAS_CONFIG -r $CIMAS_WD -g models

cimas cleanup-orphan-files -f $CIMAS_CONFIG -r $CIMAS_WD -g models

git -C $CIMAS_WD/<repo> diff --cached     # review every deletion

cimas cleanup-orphan-files -f $CIMAS_CONFIG -r $CIMAS_WD -g models \
  --push-after -b cleanup-orphans-YYYY-MM-DD -m 'Remove orphan Cimas files'

cimas open-prs -f $CIMAS_CONFIG -r $CIMAS_WD -b cleanup-orphans-YYYY-MM-DD
----

Two traps in the scope:

* A repo that no group lists is reached by `-g all` and by no other `-g` value.
  The audit prints them.
* A repo whose `files:` is empty has *every* Cimas-written file orphaned, not
  one.


=== Un-mapping a file on purpose

Record it in `cimas.yml` where the mapping was:

[source,yaml]
----
    files:
      # unmapped 2026-09-03 (relaton/support#65): rake.yml is custom here. It
      #   runs the dependent-gem tests, which the shared template does not.
      # .github/workflows/rake.yml: gh-actions/master/rake.yml
      .github/workflows/release.yml: gh-actions/master/release.yml
----

`spec/cimas_unmapped_markers_spec.rb` fails on a comment inside a `files:` block
that starts no marker, and on a repo whose `files:` is empty and carries none.

The marker records the intent. It does not protect the file: only the
destination repo can do that, by deleting the two Cimas header lines, as
`relaton-data-itu` did for its `crawler.yml`. Until then the file needs a `keep`
row in `orphan-allowlist.yml`.
