= relaton-data-* GitHub Pages index configs

Source of truth for the per-repo settings behind each `relaton-data-*` repo's
GitHub Pages index site (relaton/relaton#48).

The site is built by the shared reusable workflow
`relaton/support/.github/workflows/data-deploy.yml`, which runs `relaton index`
over the repo's `data/` folder and deploys the result to Pages. It reads this
directory's `configs.yml` for the page's `title`, `favicon` and `description`.

[IMPORTANT]
====
`relaton index` replaced a Jekyll build in support#58 (relaton/relaton#83). The
`_config.yml` material below — `../bin/gen-data-index-config`, `generated/`, the
theme merge, the pubid rule — describes that superseded path and is kept because
`configs.yml` still carries the fields it used. Only `display`, `favicon` and
`description` reach the live build today; retiring the rest is follow-up work.
====

== Files

`configs.yml`:: The verified per-repo table: `repo`, `display`, `source`
  (published INDEXFILE the current relaton consumer reads), `branch` (the repo's
  real default branch — drives `baseurl`), and `pubid_class` (blank for flat
  indexes). Edit this to change any repo's config.
+
It has two consumers. `display`, `favicon` and `description` are also the
branding the live `relaton index` build renders (see the note below), so an edit
to those fields changes a repo's published page on its next deploy — no data-repo
change involved.
`../bin/gen-data-index-config`:: Renders a repo's `_config.yml` from `configs.yml`.
`../bin/index-branding`:: Resolves one repo's `title`/`favicon`/`description` from
  `configs.yml` and prints them in `$GITHUB_OUTPUT` form. Run by the "Resolve
  branding" step of `data-deploy.yml`; useful by hand to preview what a repo will
  publish (`bin/index-branding relaton/relaton-data-iana`).
`generated/`:: The committed snapshot of all 29 rendered `_config.yml` files (one
  per target repo) — the exact bytes to commit into each data repo. Regenerate with
  `../bin/gen-data-index-config --out data-index/generated`; kept honest by
  `spec/generated_configs_spec.rb`.
`../bin/check-data-pages`:: Confirms each repo's Pages site and raw index URL return
  200 (the "confirm each site returns 200" gate). Run it after the rollout lands.

== Why `_config.yml` lives in each data repo (not Cimas)

`_config.yml` is unique per repo and is *repo-owned* — exactly like
`relaton-data-oasis`, `-w3c`, and `-ids` already keep theirs. Cimas manages only
the byte-identical plumbing (`deploy.yml`). This generator is the single place
the per-repo configs are produced; the output is committed into each
data repo, where a maintainer may further tune it without a central clobber.

== When the site rebuilds

The Cimas template `cimas-config/gh-actions/data/deploy.yml` publishes on
`workflow_run`: the Deploy run starts because the repo's `Crawler` workflow
completed, not on a cron guessed to land after it. That ordering used to be
time-based (crawler at 14:00, deploy at 15:00) and did not hold — GitHub's
scheduled dispatch drifts heavily under load, so the deploy usually indexed the
previous day's data. The `push` trigger cannot cover the gap either: the crawler
commits with the default `GITHUB_TOKEN`, and GitHub raises no workflow events
for those pushes.

The `0 18 * * *` cron is a fallback, placed clear of the crawler's observed run
window rather than one hour after its nominal cron. Note what it does *not*
cover: `types: [completed]` fires on every crawler run whether or not anything
was committed, so the cron is not there for quiet days. It covers a crawler that
never ran or was disabled, and upstream `relaton/relaton` changes that alter the
generated index — at the price of a second full build per day.

Those are the only two automatic triggers, plus `workflow_dispatch` for a human.
Neither template builds on `push` or `pull_request` any more. A PR deploy ran the
whole build — `npm ci`, the Vue compile, a full corpus parse and a Pages
artifact upload — and then skipped the deploy job, because publication is gated
on the repo's default branch; and a PR crawl fetched an
entire corpus and discarded it, since the shared `crawler.yml` gates its "Push
data" step on `github.event_name != 'pull_request'`. `push` bought little
either: on Deploy it never fired on crawler commits at all (`GITHUB_TOKEN`
pushes raise no events), and on Crawler it only re-ran what the cron runs anyway.
The trigger sets are pinned by `spec/data_deploy_caller_template_spec.rb`.

Two costs to know about. A hand-committed data or config fix no longer
republishes immediately — it waits for the `0 18 * * *` cron, or a
`workflow_dispatch`. And since each data repo carries its own `crawler.rb`, the
PR run was the only non-mutating way to exercise a change to it: a dispatched
crawl is not covered by the `pull_request` gate above, so it commits and pushes
its crawled corpus to whichever branch it runs on.

[CAUTION]
====
A required status check that can no longer be triggered leaves every future PR
permanently pending, so a repo listing `Deploy` or `Crawler` as required would
break on this change. Checked at the time of writing: *no* `relaton-data-*` repo
has branch protection configured at all, so there is nothing to unpick. Re-check
before a much later sync — `gh api` writes its error body to stdout on a 404, so
filter after it rather than with `--jq`:

[source,sh]
----
for r in $(gh repo list relaton --limit 200 --json name -q '.[].name' | grep '^relaton-data-'); do
  b=$(gh repo view "relaton/$r" --json defaultBranchRef -q .defaultBranchRef.name)
  gh api "repos/relaton/$r/branches/$b/protection" 2>/dev/null |
    jq -e -r --arg r "$r" \
      '.required_status_checks.contexts // [] | select(length > 0) | "\($r): \(.)"'
done
----

What PR-time validation remains is thinner than it looks: `check_data.yml` keeps
its own `push`/`pull_request` triggers, but `cimas.yml` maps it into only 3 of
the 30 repos (bipm, iho, iso). For the other 27, a PR touching `data/**` now runs
no CI at all.
====

Two things a caller deliberately does *not* declare, because `data-deploy.yml`
declares them centrally for the whole fleet: the `if:` that skips a `workflow_run`
whose crawler failed, and the Pages `concurrency` group. That group is keyed on
the deploy job's own default-branch gate, so only runs that can actually publish
share a queue — GitHub keeps just one *pending* run per group and cancels it when
the next arrives, so a build that cannot publish (a `workflow_dispatch` from a
non-default branch, or a caller whose triggers have drifted) could otherwise drop
a run carrying fresh data.

[NOTE]
====
Cimas replaces `deploy.yml` wholesale in all 30 mapped repos, so nothing per-repo
can live in a caller's `with:` block and survive.

Branding no longer tries to. `title`, `favicon` and `description` come from
`configs.yml` in this directory: the shared `data-deploy.yml` sparse-checks-out
`relaton/support` at its own commit (`job.workflow_repository` +
`job.workflow_sha` — the `job` context, not `github`, which in a called workflow
describes the caller) and runs
`bin/index-branding` to resolve them per flavor. The caller template therefore
carries no `with:` block at all and is safe to sync — pinned by
`spec/data_deploy_caller_template_spec.rb`, and generalised to every synced
template by `spec/cimas_data_pages_spec.rb`.

A sync no longer clobbers anything that matters. Twelve callers still carry a
`with: {source: git}` pin from when the shared workflow defaulted to `gem`; that
default is now `git` (see "Where relaton-cli comes from" below), so those pins
set the value they would inherit anyway. A sync that *removes* them is the
cleanup, not the damage — which is the last thing that made syncing `deploy.yml`
dangerous.

Some of those callers also still pass branding inputs that are now redundant,
because `configs.yml` resolves the same values — verified equal repo by repo at
the time of writing. To re-check the current fleet rather than trusting a list
that will drift:

[source,sh]
----
for r in $(gh repo list relaton --limit 200 --json name -q '.[].name' | grep '^relaton-data-'); do
  gh api "repos/relaton/$r/contents/.github/workflows/deploy.yml" \
    -H 'Accept: application/vnd.github.raw' 2>/dev/null |
    grep -q '^    with:' && echo "$r"
done
----
====

== How the index is delivered (there is no `mode`)

`data-deploy.yml` declares no `mode` input and passes no `--mode`. There is no
per-repo or fleet-wide delivery setting left to choose.

It used to be. `relaton index` took `--mode embedded|dom|static-json`, which
traded a crawler-indexable DOM against page weight, and that choice mattered
because the entire corpus went into *one* page: `relaton-data-3gpp` serves a
151,688,883-byte `index.html`, and `relaton-data-ids` would produce ~290 MB.
Compression is not what made those unusable — GitHub Pages gzips HTML, so 3gpp's
page is only ~6.4 MB on the wire — the browser still parses the full text and
builds a DOM node per document.

relaton-cli now always emits a sharded site, which fixes the parse and heap cost
that compression could not:

----
_site/index.html            ~110 KB regardless of corpus size
_site/search-NNNN.json      summary records, 5000/shard, loaded progressively
_site/detail-NNNN.json      the rich detail fields, 500/shard, fetched on open
----

`search.json` is no longer written, and `--shard-size`, `--detail-shard-size` and
`--[no-]detail` all have working defaults, so this workflow passes none of them.

[IMPORTANT]
====
Removing the input here had to land *before* relaton-cli's change, and it cannot
be reverted piecemeal:

* Every caller builds relaton-cli from `relaton/relaton@main` — 12 of the 14 live
  callers pin `source: git` themselves, and the rest inherit it from the default
  (see "Where relaton-cli comes from" below) — so no gem release gates anything,
  and each picks upstream changes up on its next run.
* A stale `--mode` fails in a way that reads as something else. Thor's legacy
  default prints a usage error and exits *0*, so the build step goes green
  having written no `_site` at all, and the run then dies at
  `actions/upload-pages-artifact` with `tar: _site/: Cannot open: No such file or
  directory` — pointing at the wrong step. relaton-cli's change adds
  `Command.exit_on_failure?`, which will make it exit 1 where the fault is; that
  is part of the same unmerged change, not something already in place.
* The input cannot come back on its own either: a caller `with:` naming an input
  the called workflow does not declare fails the run with `Invalid input, 'mode'
  is not defined in the referenced workflow`, so callers and this file have to
  move together. No `relaton-data-*` caller passes `mode:` today, and
  `spec/data_deploy_workflow_spec.rb` pins the absence at this end.
====

Two consequences of the fetch-based page worth knowing: it must be served over
`http(s)://`, so a local `file://` preview of `_site/index.html` now shows an
empty index; and the shards must not be pre-compressed in the deploy — Pages
gzips them already, and a stored `.json.gz` would be served as
`application/gzip` with no `Content-Encoding` and never inflated.

== Where relaton-cli comes from (`source`)

`data-deploy.yml`'s `source` input picks where the `relaton-cli` that runs
`relaton index` comes from. It defaults to **`git`**:

`git` (default):: check out `relaton/relaton` at `relaton-ref` (`main`), compile
  the Vue frontend with `npm ci && npm run build` (relaton-cli's `frontend/dist`
  is gitignored, so it is not in the checkout), resolve the gems through a
  generated `$RUNNER_TEMP/Gemfile.index`, and run `bundle exec relaton index`.
`gem`:: `gem install relaton-cli` and run `relaton index`. Ruby only — the gem
  ships the precompiled bundle.

The default is `git` for two reasons. No released relaton-cli has the `index`
command (latest stable 2.1.2, 2026-05-29; `3.0.0.pre.alpha.1` predates it), so a
`gem` build cannot work — it exits 0 printing `Could not find command "index"`,
writes no `_site`, and the run dies at `actions/upload-pages-artifact`. And
`relaton index` is being iterated on too quickly to cut a release per change.

**Flip back to `gem` once relaton v3 is stable and released.** It is one line in
`data-deploy.yml`, pinned by `spec/data_deploy_workflow_spec.rb`, which also
asserts both paths still exist so the revert stays one line. One caveat: the
twelve callers that still pin `source: git` themselves keep building from git
until a `cimas sync` drops those pins. A release is also what ends the `git`
path's cost: Node, `npm ci` and a frontend compile on every build.

`relaton-ref` deliberately stays `main` rather than a known-good SHA (contra
`relaton__support__data-deploy-trigger-and-concurrency.md` §3): bumping a pin per
upstream change is the same treadmill as releasing. A broken upstream is not a
broken site — `deploy` runs only when the build succeeds, so each repo keeps
serving its last successful deployment; you get stale sites and red runs. The
input remains available for a repo that needs to freeze.

Cost, measured on `relaton-data-3gpp` (88,464 documents) from its 2026-08-12
Deploy run — the "~10 minute build" figure that earlier notes carried was wrong
by roughly 4×:

----
npm ci + Vue compile + bundle       61 s
relaton index (88,464 documents)    80 s
whole run, checkout -> deployed   ~3 min 10 s
----

Small flavors (bipm, iana) finish in under two minutes.

== The pubid rule

The theme plugin renders a structured index `:id` (a Hash) by instantiating a
flavor class. `pubid_class` therefore must match the class relaton uses for that
flavor's index in `relaton/lib/relaton/<flavor>/data_fetcher.rb`
(`Relaton::Index.find_or_create(..., pubid_class:)`) — the external
`Pubid::<Flavor>::Identifier`. Write it *without* a leading `::` (the plugin
resolves it via `Object.const_get`). Flat indexes whose `:id` is a plain string
take no `pubid_*` keys.

== Rendering readiness (verified against published indexes)

[NOTE]
====
The theme plugin now reconstructs a `_type:`-tagged Hash `:id` via
`Pubid::<Flavor>::Identifier.from_hash(...)` (hand-off
`relaton__jekyll-theme-relaton-data-index__render-pubid-structured-ids.md`, landed) and
degrades to a compact fallback string if that gem is missing. For real DocIDs the pubid
gem must therefore be in the *build* bundle — which is why the deploy bundle
(`cimas-config/gh-actions/data/Gemfile.deploy`) `eval_gemfile`d each data repo's own

bundle, the tier-C flavors below rendered citable DocIDs rather than a fallback like
`2010 IEC IEC`. That bundle has since been deleted along with its 29 Cimas
mappings: `relaton index` resolves its own dependencies (`source: gem` installs
relaton-cli, `source: git` writes `$RUNNER_TEMP/Gemfile.index`), and it reads the
data YAML directly without calling pubid at all.

`configs.yml` covers *29 repos*: the 26 rollout targets plus the 3 already-live
(*ids, oasis, w3c*), folded in so the generator is the single source for every site.
The 3 live ones carry per-repo `favicon`/`description` overrides (and w3c a
`pubid_require: relaton/w3c/pubid`); regenerating their `_config.yml` reproduces the
live site (with `baseurl` corrected from `/main/` to their real default `/v2/`).

Live (200): *relaton-data-ids, -oasis, -w3c* — already rolled out.

Pending (Pages 404): *the other 26 repos in `configs.yml`*. Every one's published index
(`<baseurl><source>`) already returns 200 — i.e. the data side is ready.

Pages *enablement* state (verified via `gh api repos/relaton/relaton-data-<repo>/pages`):

* *Already enabled* (`build_type: workflow`, source = default branch, no build
  published yet so the site 404s) — the *20 `v2`-default repos*. These need only
  steps 2–3 below; *skip step 1*.
* *Not enabled* (Pages API 404) — the *6 `main`-default repos*: *adobe, easc, gost,
  itu, jcgm, oiml*. These need step 1, which requires *repo admin* (a plain
  `push`/`repo` token gets HTTP 404 from the Create-Pages endpoint). *itu* was
  added after this section's 2026-08-03 sweep and re-checked 2026-08-15.

Re-check current state any time with:

bin/check-data-pages              # site + raw-index for all 29

== Rollout

Do these per target repo (or batch the Cimas step across all of them). Steps 1–3
all happen *in the data repo* / on GitHub — this `support` repo only holds the
source of truth and tooling.

. *Enable GitHub Pages* (source: *GitHub Actions*) — *only for the 5 not-yet-enabled
  `main`-default repos* (adobe, easc, gost, jcgm, oiml); the 20 `v2` repos already
  have it (see Status). *Requires repo admin* — a `push`-only token gets HTTP 404:
+
[source,sh]
----
gh api -X POST repos/relaton/relaton-data-<repo>/pages \
  -f 'build_type=workflow'      # 409 if already enabled (safe to ignore)
----
. *Commit the `_config.yml`* onto the repo's default branch (from `configs.yml`'s
  `branch:` — `v2` for most, `main` for adobe/easc/gost/jcgm/oiml). Use the
  committed snapshot:
+
[source,sh]
----
# snapshot already rendered in data-index/generated/
cp data-index/generated/<repo>_config.yml <data repo>/_config.yml
# (or regenerate on the fly: bin/gen-data-index-config <repo>)
----
. *Roll the Cimas plumbing* (`deploy.yml`) to every data repo —
  from the support repo root, per `../README.adoc`:
+
[source,sh]
----
cimas sync -f $CIMAS_CONFIG -r $CIMAS_WD -d $CIMAS_MASTER_DIR -g data
cimas push -f $CIMAS_CONFIG -r $CIMAS_WD -b data-pages -m 'Pages deploy' -g data
cimas open-prs -f $CIMAS_CONFIG -r $CIMAS_WD -b data-pages -m 'Pages deploy' -g data
----
. *Confirm* the `Deploy` workflow goes green and each site returns 200:
+
[source,sh]
----
bin/check-data-pages              # exits non-zero until every repo is 200
----
+
The site should list DocID -> file with working pagination and a citable DocID
per row.

TIP: Start with Tier A (renders cleanly today); Tier B/C needed the flavor pubid
gem in the build bundle, which the now-deleted
`cimas-config/gh-actions/data/Gemfile.deploy` supplied by `eval_gemfile`ing each
repo's own Gemfile. See "Rendering readiness".

NOTE: `configs.yml` and `../cimas-config/cimas.yml` must agree on every repo's
`branch:` and both must map `deploy.yml` (and, since the Jekyll build was
retired, must map no `Gemfile.deploy`); a drift silently
skips the publish (the deploy job only runs on the repo's default branch).
`spec/cimas_data_pages_spec.rb` enforces this — run `bundle exec rspec` after
editing either file.
